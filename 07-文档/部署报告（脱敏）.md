## 四、服务器部署结构

```
/opt/hostvote/
├── app/     代码目录（升级时整体覆盖，不影响数据）
│   ├── .env            运行配置（管理员初始密码、端口、目录，权限 600）
│   └── scripts/        运维脚本（备份 / 重置数据 / 重置密码 / 端到端测试 / 截图）
├── data/    数据目录
│   ├── hostvote.db     SQLite 数据库（WAL 模式）
│   ├── uploads/        选手照片
│   ├── INITIAL_ADMIN.txt   初始管理员凭据
│   └── INITIAL_CODES.txt   初始密码条清单
├── backup/  每日自动备份（保留最近 14 份）
└── logs/    app.log / app.err.log / backup.log
```

| 组件 | 说明 |
|---|---|
| 运行时 | Node.js **v24.21.0**（/usr/local/bin/node，官方二进制包，无需编译） |
| 依赖 | 全部为纯 JS 包，**零原生模块**（数据库用 Node 内置 `node:sqlite`），服务器上不需要 gcc/make |
| 进程守护 | systemd 服务 `hostvote.service`（开机自启、崩溃 3 秒后自动重启、安全加固） |
| 反向代理 | Nginx 同时监听 **80** 与 **8080** → 反代 `127.0.0.1:3000`；应用只监听本机，不直接对外暴露 |
| 定时备份 | `/etc/cron.d/hostvote-backup`，每天 02:00 自动备份数据库与照片 |
| 防火墙 | 系统 firewalld/ufw 未启用；云安全组已放行 80、8080、22 |

## 六、上线后你需要做的 3 件事

1. **录入选手**（后台 → 选手管理）
   把 10 位占位选手（当前名称为「选手01」…「选手10」）改成真实姓名，并逐个上传照片。
   照片建议竖版（比例 3:4），上传后自动替换旧图，投票页会以卡片形式展示。
   若有选手退出，请用「停用」而不是删除（历史数据保留）。

2. **生成/打印密码条**（后台 → 密码条管理）
   - 大众评审：按实际人数批量生成 → 打印 → 裁剪发放（每人一张）。
   - 专业评审：确认 4 条密码条已绑定评审席 1-4，标签可改成评审姓名（如「专业评审-张老师」）。

3. **核对规则并开启投票**（后台 → 系统设置 / 赛程与开关）
   系统设置中按赛事规程填写每票可勾选人数、赋分梯度、评审席位数、得分上限与两场权重。
   赛程与开关中设置开始/截止时间 → 点「开启」。到截止时间系统自动锁定并完成统计，无需人工操作。

比赛期间在「仪表盘」实时看票与排名；纸质票或临时情况走「手动赋分」（含改前/改后排名影响预览）；
结束后在「数据导出」一键导出 Excel 归档。

## 九、安全提示

- 本系统按需求**未启用 HTTPS**（密码条仅作身份凭证）。密码条为 8 位、32 字符集的随机码（约 1.1 万亿种组合），

- 所有人工修改都留有操作日志（谁、何时、改了什么，含前后快照），可随时导出核对。
- 每日自动备份 14 天；重大节点（开赛前、截止后）建议手动再导出一次 Excel 存档。

| 500 | 2500 | 0 | 3.4 s | 5 ms | 2.6 s | 3.3 s |
| 1000 | 5000 | 0 | 6.8 s | 5 ms | 5.1 s | 6.7 s |

**结论：200 人甚至 1000 人同时提交都不需要升级服务器配置。**

压测中发现并修复的两个隐患（平时看不出来，大场面才会暴露）：
1. **nginx `worker_connections` 为默认 768** —— 500 人同时访问时出现 `ECONNRESET`
   （500 客户端连接 + 500 上游连接 = 1000 > 768）。已提高到 4096 并开启 `multi_accept`、
   设置 `worker_rlimit_nofile 65535`，复测 500/1000 并发零失败。
2. **密码条登录限流原先硬编码为「同一 IP 每 5 分钟 900 次」** —— 现场若整个校园网共用出口 IP，
   所有登录都计在同一个 IP 上，人数一多会误伤真实投票者。已改为后台可配置
   （「系统设置 → 同一 IP 允许的登录次数 / 限流窗口」），默认 5000 次 / 5 分钟，
   生产环境当前设为 10000 次 / 5 分钟（200 人约需 200-400 次登录，余量 25 倍以上）。

### 2026-10-11 18:00 —— 全面深度审计（投票与计分重点）
以"找 bug"为目标做了一轮深度审计，新增审计脚本 103 项检查，**发现并修复 3 个真实缺陷**：

1. **【安全/逻辑】停用的密码条仍可继续投票与打分**
   后台把某张密码条停用后，该用户浏览器里已存在的会话仍然可以提交投票（只有"打开页面"这一层被拦住）。
   影响：现场若因发放错误需要停用某张密码条，无法真正阻止其投票。
   **已修复**：投票与打分提交时统一校验密码条启用状态，停用后立即失效（返回 403 并提示原因）。

2. **【数据一致性】选手停用/删除后，结果表残留旧行**
   `results` / `final_results` 只在重算时"新增或更新"当前在赛选手，从不删除已退出选手的行。
   影响：把选手停用（例如临时退出）后，「结果与排名」页与公示榜**仍会显示该选手及其旧分数**；
   选手被删除后还会留下孤儿记录。
   **已修复**：重算时清理已停用/已删除选手的残留行；并补充 `scripts/doctor.mjs` 用于事后体检。

3. **【误导】手动赋分的"改前→改后"预览显示错了赛事的票数**
   预览接口在 `view=final` 时，把"票数 / 赋分 / 专业均分"三列取成了**个人赛**的数值，
   无论你在改小组赛还是个人赛。
   影响：预览显示的票数、赋分与实际执行结果不一致，会让人误判改动影响。
   **已修复**：一律取所编辑赛事的数据，并在预览表末尾额外增加「最终总成绩 / 总名次」两列。

另外做了 3 项加固：
